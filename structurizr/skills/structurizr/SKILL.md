# Structurizr / C4 architecture documentation

This skill produces or edits a `workspace.dsl` file (Structurizr DSL, the C4 model) at the
root of the user's repository, validates it, and links ADRs when the repository has them.

## The contract

These rules exist because a workspace.dsl is *documentation other people will trust*. A
fabricated technology choice or an invented relationship is worse than a gap — the gap gets
asked about, the fabrication gets believed.

1. **Never invent architecture.** Do not assign technologies, create elements, or draw
   relationships the user (or the code you inspected) did not establish. When something is
   missing or ambiguous, ask. It is fine to choose cosmetic defaults yourself (colors, layout
   direction, view keys) — those carry no architectural claims.

2. **Classify before you model.** The most common C4 mistake is putting something at the
   wrong abstraction level (a system drawn as a container, a deployment concern drawn on a
   container view). When you are not sure whether something is a software system, a
   container, a component, or a deployment concept, read
   `references/c4-classification.md` — it has litmus tests and a ready-made question bank.
   Ask the user the 2–4 questions that actually decide the case (ownership, deploy unit,
   runs-or-stores) instead of guessing. Don't ask what you can verify yourself in the repo.

3. **Modern syntax only** (Structurizr DSL v6+). Never emit these legacy/removed keywords:

   | Never write | Write instead |
   |---|---|
   | `enterprise { }` | `group "Name" { }` |
   | `!extend`, `!ref` | `!element` / `!relationship` (and `!elements` / `!relationships`) |
   | `branding { }` (removed in v6) | themes |
   | `themes a b` (plural list) | one `theme <name-or-url>` line each |
   | `dashed true` / `dashed false` in styles | `style solid`, `style dashed`, or `style dotted` |
   | `location` on person/system | `group` + tags |

4. **Minimal diffs when editing.** Preserve existing identifiers, naming style, ordering,
   styles, and view keys; add what was asked and nothing else. Renaming elements or view keys
   silently destroys the diagram layout the user arranged in the UI (layout is stored in
   `workspace.json`, keyed to the model).

5. **Never hand-edit `workspace.json`.** It is generated by Structurizr from `workspace.dsl`
   and additionally holds manual diagram layout. The DSL file is the only source you touch.

## Workflow

### 1. Discover the current state

- Look for `workspace.dsl` at the repo root (the expected location); also glob `**/*.dsl`
  in case the project keeps it elsewhere — if so, edit it where it lives.
- Look for ADR directories: `docs/adr`, `docs/adrs`, `docs/decisions`, `adr/`,
  `docs/architecture/decisions`. Peek at one file to identify the format (see step 5).
- Skim the repo (compose files, deploy manifests, service directories, READMEs) to ground
  your understanding — but remember rule 1: code tells you what exists, the user tells you
  what it means.

### 2. Understand and classify the system

Build a mental model: who uses it (people), what the system(s) are, what runs inside them
(containers), what is external. Apply the litmus tests from
`references/c4-classification.md`. The recurring traps, condensed:

- **Container** = something that must be *running* for the system to work, or a *data
  store* — an API, SPA, mobile app, worker, cron job, serverless function, database,
  queue, blob store. NOT a Docker container per se, NOT a library/JAR/module.
- **Software system vs container** for a service is decided by *ownership*: one team owns
  it and sees its internals → container(s) inside that team's system; another team owns it
  or it's third-party SaaS → separate (external) software system.
- **Microservices** owned by one team: each service = a `group` of containers (typically
  API + database schema). Owned by different teams: promote each to a software system.
- **Queues/topics** are containers (the queues themselves, not the broker) — or just a
  "via" label on the relationship when that detail isn't worth a box.
- **API gateways, load balancers, firewalls** are deployment concepts: model them as
  `infrastructureNode` in a deployment environment, never as containers on a container view.

If after this any element is still ambiguous, stop and ask. Present your proposed
classification of the *clear* parts so the user only has to resolve the open points.

### 3. Choose the views

Read `references/diagrams.md` when in doubt. Defaults that follow C4's own recommendations:

- **System context + container views: always** (for a system-scoped workspace).
- **System landscape**: when the user describes multiple systems of an organization.
  Use a landscape-scoped workspace (no containers) — see step 4.
- **Deployment views**: one per environment, when the user describes infrastructure.
- **Dynamic views**: sparingly — only for flows the user asked for or that are genuinely
  non-obvious. Every step must be backed by a relationship that exists in the model.
- **Component views**: only on request or clear value; **code-level**: effectively never
  (IDEs generate it on demand).

Create only what was asked for plus the always-recommended pair. More diagrams ≠ better
documentation; each one is a maintenance liability.

### 4. Write the DSL

Always read `references/dsl-reference.md` (core syntax) before writing DSL. Then read
ONLY the pattern file the task actually needs — every file you read costs tokens on every
invocation, and most tasks need none of them:

- Deployment environments, gateways/load balancers, Docker/K8s/AWS, multi-environment →
  `references/deployment-patterns.md`
- Microservices, queues/topics, landscape/multiple systems, splitting the model across
  files → `references/modeling-patterns.md`
- Archetypes, workspace extension (`!element`), filtered/custom/image views,
  perspectives, scripts/plugins → `references/dsl-advanced.md`

House conventions for new workspaces:

```
workspace "Name" "One-line description." {

    !identifiers hierarchical

    model {
        u = person "User" "Why they use the system."

        s = softwareSystem "System" "What value it delivers." {
            api = container "API" "What it is responsible for." "Go"
            db = container "Database" "What it stores." "PostgreSQL" {
                tags "Database"
            }
        }

        ext = softwareSystem "Payment Provider" "Third-party PSP." {
            tags "External"
        }

        u -> s.api "Manages orders using" "HTTPS"
        s.api -> s.db "Reads from and writes to" "SQL/TCP"
        s.api -> ext "Authorizes payments using" "HTTPS"
    }

    views {
        systemContext s "SystemContext" {
            include *
            autoLayout
        }

        container s "Containers" {
            include *
            autoLayout
        }

        styles {
            element "Element" {
                background #1168bd
                color #ffffff
            }
            element "Person" {
                shape person
            }
            element "Database" {
                shape cylinder
            }
            element "Queue" {
                shape pipe
            }
            element "External" {
                background #999999
                color #ffffff
            }
        }
    }

    configuration {
        scope softwaresystem
    }
}
```

Why these conventions:

- `!identifiers hierarchical` — lets container names repeat across systems and keeps the
  workspace extendable later.
- **Every element gets a description; every container gets a technology.** The C4 review
  checklist demands both; diagrams must be readable by someone who wasn't in the room.
- **Relationship labels are specific and directional** — "Publishes click events to", not
  "Uses". The label must read correctly along the arrow's direction. Inter-process
  relationships also get a technology/protocol.
- **Tags + styles, not ad-hoc colors**: `Database` → cylinder, `Queue` → pipe, `External` →
  grey, person shape for people. Consistent encodings double as the diagram legend.
- **Stable, descriptive view keys** (`"SystemContext"`, `"Containers"`,
  `"Deployment-Live"`) — keys identify views across exports and layout sessions; changing
  them later orphans saved layout.
- `autoLayout` on every view (direction `lr`/`tb` as fits the flow) — the user can still
  drag elements in the UI, which then persists to `workspace.json`.
- `configuration { scope softwaresystem }` for one-system workspaces,
  `scope landscape` for landscape workspaces (these must not define containers).
- Write element names and descriptions in the language the user used to describe their
  system; DSL keywords are always English.

### 5. Link ADRs

If the repo has ADRs (step 1), attach them with `!adrs` at the right scope — workspace
level normally; inside a `softwareSystem`/`container` block only when the ADRs clearly
belong to that one element. Detect the format:

- Files like `0001-record-architecture-decisions.md`, sections `## Status` / `## Context` /
  `## Decision` / `## Consequences` → adr-tools format (the default):
  `!adrs docs/adr`
- MADR layout (`docs/decisions/`, frontmatter with `status:`/`date:`, "Context and Problem
  Statement") → `!adrs docs/decisions madr`
- log4brains → `!adrs <path> log4brains`

The path is relative to the DSL file. Don't create ADRs the user didn't ask for; if there
are none, simply don't emit `!adrs`.

### 6. Validate — always, before declaring done

Prefer the **Structurizr MCP server** (exposes DSL validate/parse/inspect tools and
Mermaid/PlantUML export; this plugin's bundled MCP config expects it at
`http://localhost:3000/mcp`):

1. Check whether Structurizr MCP tools are available in the session (e.g. via ToolSearch —
   tool names contain "structurizr"). If yes, run the DSL validation tool on the workspace
   and fix every reported error, re-validating until clean.
2. If MCP tools are not connected, fall back to the Docker image:
   `docker run --rm -e STRUCTURIZR_THEMES=/usr/local/structurizr-themes -v "$PWD":/usr/local/structurizr structurizr/structurizr validate -workspace workspace.dsl`
   (the env var lets bundled theme names like `amazon-web-services-2025.07` resolve)
3. If neither is available, say so explicitly and give the user both the `validate`
   command above and the command that starts the MCP server, so the next session can
   validate through it:
   `docker run --rm -p 3000:3000 -e PORT=3000 -e STRUCTURIZR_THEMES=/usr/local/structurizr-themes structurizr/mcp -dsl -mermaid -plantuml`
   — and never imply the file was validated when it wasn't.

Common parse errors: referencing an element before it is defined (the DSL has no forward
references — define first, or use `this` inside the element's own block), an opening `{`
not on the same line as its statement, a flat-identifier name collision (use
`!identifiers hierarchical`), dynamic-view steps whose relationship doesn't exist in
the model, and — the classic deployment-model error — referencing an element nested in
deployment nodes by a partial path: with hierarchical identifiers you must bind an
identifier to every ancestor `deploymentNode` and use the full dotted path
(`aws.region.alb`, never bare `alb`).

### 7. Self-review

Run through the C4 review checklist in `references/diagrams.md` (titles, types,
descriptions, technologies, label direction/specificity, legend coverage). Fix what fails.

### 8. Hand off

Tell the user how to see and export the result. The image for both is
`structurizr/structurizr` (current, consolidated) — never suggest `structurizr/lite`,
it is deprecated.

- **Preview UI** at `http://localhost:8080` — live-reloads on DSL changes and saves
  manual layout into `workspace.json`:

  ```
  docker run --rm -it -p 8080:8080 -u $(id -u):$(id -g) \
      -v "$PWD":/usr/local/structurizr \
      -e STRUCTURIZR_THEMES=/usr/local/structurizr-themes \
      structurizr/structurizr local
  ```

- **Export** to `diagrams/` in another format (`plantuml`, `mermaid`, `json`, `dot`,
  `ilograph`, `d2`, `static`):

  ```
  docker run --rm -u $(id -u):$(id -g) \
      -v "$PWD":/usr/local/structurizr \
      -e STRUCTURIZR_THEMES=/usr/local/structurizr-themes \
      structurizr/structurizr export -workspace workspace.json -format <format> -output diagrams
  ```

  This reads `workspace.json` (where saved layout lives), so preview with the UI at
  least once first — or export straight from the DSL with `-workspace workspace.dsl`.

If the user has their own wrappers/aliases around these images, respect those instead.

## Reference files

Read only what the task needs — each file read is a per-invocation token cost.

| File | Read it when |
|---|---|
| `references/dsl-reference.md` | Always, before writing any DSL — core signatures for elements, relationships, views, styles, deployment, `!adrs`, themes, configuration. |
| `references/c4-classification.md` | Anything is ambiguous: system vs container, microservices ownership, queues, serverless, shared libs. Includes the clarifying-question bank. |
| `references/diagrams.md` | Choosing which diagrams to create + the pre-delivery review checklist. |
| `references/deployment-patterns.md` | Deployment work: `-/>` rerouting, Docker/K8s/AWS nesting, multi-environment, deployment groups. |
| `references/modeling-patterns.md` | Microservices, messaging, landscape/system catalog, monorepo composition. |
| `references/dsl-advanced.md` | Rare: archetypes, workspace extension, filtered/custom/image views, perspectives, scripts/plugins. |
