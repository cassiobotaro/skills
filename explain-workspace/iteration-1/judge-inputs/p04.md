## The reply given to the user

```
   1  **Um mutex é um cadeado que garante que só uma goroutine por vez mexa em um dado compartilhado.** O nome vem de *mutual exclusion* (exclusão mútua).
   2  
   3  Estou assumindo que você conhece JavaScript, mas ainda não viu goroutines. Se já conhece, me diga e eu pulo essa parte.
   4  
   5  **Por que isso não existe no JS do dia a dia**
   6  
   7  O JS roda seu código em uma thread só. Uma função não é interrompida no meio por outra, então dois trechos de código nunca mexem na mesma variável ao mesmo tempo.
   8  
   9  Em Go, goroutines podem rodar de verdade em paralelo, em vários núcleos. Aí aparece um problema novo:
  10  
  11  ```go
  12  var contador int
  13  
  14  func main() {
  15      var wg sync.WaitGroup
  16      for i := 0; i < 1000; i++ {
  17          wg.Add(1)
  18          go func() {
  19              defer wg.Done()
  20              contador++ // parece uma operação só, mas não é
  21          }()
  22      }
  23      wg.Wait()
  24      fmt.Println(contador) // esperado: 1000. Real: muitas vezes menos
  25  }
  26  ```
  27  
  28  `contador++` são três passos: ler o valor, somar 1 e gravar. Suponha que duas goroutines leiam `41` ao mesmo tempo. As duas gravam `42`, e um incremento se perde. Isso se chama *data race*, e o resultado muda a cada execução.
  29  
  30  **A correção com mutex**
  31  
  32  ```go
  33  var (
  34      mu       sync.Mutex
  35      contador int
  36  )
  37  
  38  go func() {
  39      defer wg.Done()
  40      mu.Lock()   // se outra goroutine já tem o cadeado, espera aqui
  41      contador++
  42      mu.Unlock() // libera para a próxima
  43  }()
  44  ```
  45  
  46  Só quem passou por `Lock()` executa o trecho até o `Unlock()`. As outras ficam esperando na fila. Agora o resultado é sempre 1000.
  47  
  48  **Uma analogia, com limite**
  49  
  50  Pense num banheiro com uma chave: quem pega a chave entra e os outros esperam. A chave é o mutex, o banheiro é o trecho protegido (a *seção crítica*) e esperar na porta é o `Lock()` bloqueando. A analogia falha em um ponto: o mutex não protege a variável em si. Ele só funciona se todo o código que acessa `contador` pegar o cadeado. Se um único lugar esquecer, a proteção some e o compilador não avisa.
  51  
  52  **Na prática, em Go**
  53  
  54  - Use `defer mu.Unlock()` logo depois do `Lock()`. Assim você não esquece de liberar, mesmo se a função retornar cedo ou der `panic`.
  55  - O mutex costuma ficar dentro de uma struct, ao lado do dado que protege.
  56  - Para achar races, rode `go run -race` ou `go test -race`. Isso é uma ferramenta que conheço bem, mas confira na documentação a saída exata na sua versão.
  57  - Este é o resumo para começar. Existem também `sync.RWMutex`, `sync/atomic` e canais, que resolvem problemas parecidos de outras formas. Você vai precisar deles quando o caso real for mais complexo que um contador.
  58  
  59  **Uma pergunta para testar se ficou claro:** se duas goroutines só *leem* a mesma variável e nenhuma escreve, você precisa de mutex? E se uma lê e a outra escreve?
```
