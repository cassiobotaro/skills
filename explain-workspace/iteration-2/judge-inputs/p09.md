## The reply given to the user

```
   1  Um **mutex** (de *mutual exclusion*, exclusão mútua) é um "cadeado" que garante que só **uma goroutine por vez** mexa em um dado compartilhado.
   2  
   3  ## Por que isso importa em Go (e não no JS)
   4  
   5  No JavaScript você quase nunca precisa disso. Seu código roda em uma única thread, com event loop. Entre um `await` e outro, ninguém mexe nas suas variáveis.
   6  
   7  Em Go, goroutines rodam **de verdade em paralelo**, em várias threads do sistema. Se duas delas alteram a mesma variável ao mesmo tempo, você tem uma *race condition*:
   8  
   9  ```go
  10  package main
  11  
  12  import (
  13  	"fmt"
  14  	"sync"
  15  )
  16  
  17  func main() {
  18  	contador := 0
  19  	var wg sync.WaitGroup
  20  
  21  	for i := 0; i < 1000; i++ {
  22  		wg.Add(1)
  23  		go func() {
  24  			defer wg.Done()
  25  			contador++ // PERIGO: ler, somar e escrever não é atômico
  26  		}()
  27  	}
  28  
  29  	wg.Wait()
  30  	fmt.Println(contador) // esperado 1000, mas pode dar 937, 981...
  31  }
  32  ```
  33  
  34  O `contador++` são três passos (ler, somar, gravar). Duas goroutines podem ler o mesmo valor, e uma atualização se perde.
  35  
  36  ## A solução: `sync.Mutex`
  37  
  38  ```go
  39  var mu sync.Mutex
  40  contador := 0
  41  
  42  // dentro de cada goroutine:
  43  mu.Lock()    // "pego a chave"; se outra goroutine está com ela, espero
  44  contador++
  45  mu.Unlock()  // "devolvo a chave"
  46  ```
  47  
  48  Agora o resultado é sempre 1000. O trecho entre `Lock()` e `Unlock()` é chamado de **seção crítica**: só uma goroutine entra por vez.
  49  
  50  ## Idiomático: `defer Unlock()`
  51  
  52  Para não esquecer de destravar (em um `return` antecipado ou um `panic`, por exemplo), use `defer`:
  53  
  54  ```go
  55  type Contador struct {
  56  	mu sync.Mutex
  57  	n  int
  58  }
  59  
  60  func (c *Contador) Inc() {
  61  	c.mu.Lock()
  62  	defer c.mu.Unlock()
  63  	c.n++
  64  }
  65  ```
  66  
  67  Repare que o mutex fica **dentro da struct**, junto do dado que ele protege. Esse é o padrão comum em Go.
  68  
  69  ## Pontos de atenção
  70  
  71  - **Nunca copie um mutex** depois de usado. Use ponteiros (`*Contador`), como no exemplo acima. O `go vet` avisa sobre isso.
  72  - **Deadlock**: se você dá `Lock()` duas vezes na mesma goroutine sem `Unlock()`, ela trava para sempre.
  73  - **`sync.RWMutex`**: permite vários leitores ao mesmo tempo, mas só um escritor. Útil quando se lê muito mais do que se escreve.
  74  - **Detectar bugs**: rode `go run -race main.go` (ou `go test -race`). O detector de corrida do Go aponta acessos concorrentes sem proteção.
  75  
  76  ## Mutex ou channel?
  77  
  78  Go também tem *channels*, e o lema é "compartilhe memória comunicando, não comunique compartilhando memória". Na prática:
  79  
  80  - **Mutex**: para proteger um estado simples compartilhado (contadores, caches, mapas).
  81  - **Channel**: para passar dados ou coordenar o trabalho entre goroutines.
  82  
  83  Nenhum é "o certo" sempre. Para um contador ou um mapa, o mutex costuma ser mais simples.
  84  
  85  Se quiser, posso mostrar como proteger um `map` (que em Go **não** é seguro para uso concorrente) ou comparar com a versão usando channels.
