  14  
  15  Hoje a API pública não limita o tráfego por cliente. No incidente INC-4412, um cliente com uma integração mal feita derrubou a API para todos por 25 minutos. Este documento propõe um rate limit por token de API no gateway (Kong), com janela deslizante e contadores no Redis de sessão, limites por plano e resposta `429` com `Retry-After`.
  16  
  17  ## Contexto
  18  
  19  Em 2026-11-21, um cliente com uma integração mal feita enviou 40x o tráfego normal e a API ficou indisponível para todos os clientes por 25 minutos (INC-4412). Não existe hoje limite por cliente na API pública.
  20  
  21  O gateway é o Kong. O Redis que guarda as sessões já está em uso e é a base proposta para os contadores.
  22  
  23  ## Objetivos
  24  
  25  - Nenhum token excede o limite do seu plano por mais de 1 segundo.
  26  - A API suporta um cliente abusivo sem degradar os demais.
  27  
  28  ## Proposta
  29  
  30  O Kong aplica o limite por token de API, antes de a requisição chegar aos serviços. Os contadores usam janela deslizante e ficam no Redis de sessão. Quando o token estoura o limite, o gateway responde `429` com o header `Retry-After`.
  31  
  32  Limites por plano:
  33  
  34  | Plano | Limite |
  35  |---|---|
  36  | Free | 10 rps |
  37  | Pro | 100 rps |
  38  | Enterprise | Negociado por cliente |
  39  
  40  O limite é por token e não por IP. Por isso clientes que compartilham um NAT não afetam uns aos outros, e esse cenário não é um risco deste desenho.
  41  
  42  ### Compensações
  43  
  44  - ✓ A requisição de um cliente abusivo é barrada no gateway, sem consumir os serviços nem a malha
  45  - ✓ Sem custo de módulo pago e sem lock-in
  46  - ✗ Um cliente legítimo em pico (por exemplo, Black Friday) pode receber `429`
  47  - ✗ O Redis de sessão passa a receber também a carga dos contadores
  48  
  49  Para o primeiro custo, o `Retry-After` diz ao cliente quando tentar de novo, e um alerta chega ao time de contas, que avisa os clientes enterprise.
  50
