```
   2

  11  | **Tags** | rate-limiting, gateway, kong, redis, api-publica, INC-4412 |
  12  
  13  ## Resumo
  14  
  15  Não existe limite de requisições por cliente na API pública, e um único cliente derrubou a API para todos no incidente INC-4412. Este documento propõe um rate limit por token de API no gateway (Kong), com janela deslizante, contadores no Redis que já usamos para sessão e limites por plano. O gateway responde 429 com o header `Retry-After` quando o token estoura o limite.
  16  
  17  ## Contexto
  18  
  19  Em 2026-11-21, um cliente com uma integração mal feita enviou cerca de 40x o tráfego normal à API pública. A API ficou fora do ar para todos os clientes por 25 minutos (INC-4412). Hoje não existe limite por cliente, então nada contém automaticamente um cliente que abusa da API.
  20  
  21  O tráfego da API pública passa pelo gateway (Kong) e pela malha de serviços antes de chegar a cada serviço. O time já opera um Redis para sessão.
  22  
  23  ## Objetivos
  24  
  25  - Nenhum token excede o limite do seu plano por mais de 1 segundo.
  26  - A API suporta um cliente abusivo sem degradar os demais clientes.
  27  
  28  Limites por plano:
  29  
  30  | Plano | Limite |
  31  |---|---|
  32  | Free | 10 rps |
  33  | Pro | 100 rps |
  34  | Enterprise | Negociado por cliente |
  35  
  36  ## Proposta
  37  
  38  O gateway conta as requisições de cada token de API em uma janela deslizante, com os contadores guardados no Redis de sessão. Quando um token ultrapassa o limite do seu plano, o gateway rejeita a requisição com 429 e inclui o header `Retry-After`, para que o cliente saiba quando tentar de novo. A requisição rejeitada não chega à malha nem aos serviços.
  39  
  40  O limite vale por token, não por IP. Clientes que compartilham um IP (NAT) não dividem a mesma cota.
  41  
  42  ### Compensações
  43  
  44  - ✓ O gateway rejeita a requisição antes de ela consumir a malha e os serviços
  45  - ✓ A proposta reaproveita o Redis que o time já opera, sem contratar nem integrar produto novo
  46  - ✓ O limite por plano dá a cada cliente uma cota previsível
  47  - ✗ Cliente legítimo em pico (Black Friday, por exemplo) pode receber 429. Mitigação: o `Retry-After` orienta o retry, e um alerta avisa o time de contas, que avisa os clientes enterprise
  48  - ✗ O Redis de sessão passa a receber a contagem de todas as requisições da API pública e pode virar ponto de contenção (ver Riscos)
  49  
  50  ## Alternativas consideradas
  51  
  52  | Alternativa | Resultado | Motivo |
  53  |---|---|---|
  54  | Não fazer nada | Descartada | Nada contém um cliente abusivo, e o INC-4412 pode se repetir |
  55  | Limitar dentro de cada serviço | Descartada | Age tarde demais: a requisição já consumiu o gateway e a malha |
  56  | Módulo pago do gateway gerenciado | Descartada | Custo e lock-in |
  57  | **Rate limit por token no gateway com Redis** | **Escolhida** | Rejeita no gateway, reaproveita o Redis existente e evita o custo e o lock-in do módulo pago |
  58  
  59  ## Riscos
  60  
  61  | Risco | Mitigação |
  62  |---|---|
  63  | O Redis de sessão vira ponto de contenção com a carga dos contadores | Medir a carga no Redis antes de ativar o enforcing |
  64  | Cliente legítimo recebe 429 em pico de tráfego | `Retry-After` na resposta e alerta para o time de contas avisar os clientes enterprise |
  65  
  66  ## Plano de entrega
  67  
  68  1. Shadow mode: o gateway só mede, sem rejeitar requisições
  69  2. Enforcing no plano free
  70  3. Enforcing em todos os planos
  71  
  72  ## Questões em aberto

  74  - Quem revisa este documento? Quais times de Plataforma, SRE e Contas entram como revisores?
  75  - O que acontece com as requisições quando o Redis fica indisponível?
  76  - Quem configura o limite negociado de cada cliente enterprise, e onde esse valor fica registrado?
  77  - Qual condição dispara o alerta para o time de contas?
  78  - Quais critérios autorizam a passagem de uma fase do plano de entrega para a seguinte, e quanto tempo dura cada fase?
```
