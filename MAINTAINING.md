# Maintaining the skills

Read this before changing anything under a `skills/` directory. It is not loaded automatically:
`AGENTS.md` points here so that a description of what the skills are expected to do stays out of
the context of eval runs (see `eval-tools/README.md`).

## Shared contract

- **Record, don't invent** is the shared contract across every skill: a skill states as fact only what the user or the repository established, and a gap is never filled with a guess. What a skill does with the gap depends on what it delivers. The skills that write a document or a diagram (`adr`, `design-doc`, `structurizr`, `mermaid-sequence`) ask: when the request is too vague to fill the sections honestly, they ask 2–4 targeted questions instead of fabricating, and the questions are the deliverable. Every other skill states its own form of the contract in its note below, and a new skill does the same instead of being added here as an exception.
- **Validation tooling**: today no skill uses an MCP at all, and `adr`, `design-doc`, `unslop`, `code-comments`, `explain` and `technical-writing` use no external tooling: `structurizr` validates, previews, and exports through the `structurizr/structurizr` Docker image (PNG/SVG only through its `<version>-playwright` variant; the regular image refuses them), and `mermaid-sequence` validates through the `minlag/mermaid-cli` Docker image with a local `mmdc` as fallback. Without Docker (or the CLI), both ship the artifact with an explicit "not validated" notice plus the command to run later — **never an install attempt, never a remote validator**.

## Per-skill notes

- **adr** — adr-tools-compatible decision log (`NNNN-slug.md`, `doc/adr` default, `.adr-dir` override, `adr init`-style seed on fresh logs, supersede/amend by editing the *old* ADR's Status section only — ADRs are otherwise immutable). The slug is ASCII-only, as adr-tools' own pipeline computes it on Linux (`tr -Ccs [:alnum:] -`): an accented letter becomes a hyphen (`decisões` → `decis-es`), never transliterated and never kept. Modern spelling `Superseded`/`Supersedes` on write; legacy `Superceded` recognized on read. Tool-parsed scaffolding (adr-tools' `Date:` label, the `## Status/Context/Decision/Consequences` headings, status words, supersede/amend verbs) stays canonical English even in a non-English log, because Structurizr's `!adrs` importer and `adr generate` parse those literals; only the prose is translated. A scope check up front hands an open design to `design-doc`, refuses to record a choice not yet made, and leaves `!adrs` wiring to `structurizr`. Since 1.5.0 the writing step (step 3; step 4 before 1.6.0) applies the `unslop` skill when it is installed, to the title text and section bodies of the record being written; scaffolding, the seed, and every existing record are out of its reach. Since 1.6.0 the third ingredient of a record is the *trade-off* (what the decision gives up in exchange for what it gets: an alternative passed over, a cost, a constraint), not a negative consequence: when the user gives none the skill asks once what was given up, never supplies one, and when the answer is that there was none it writes the record without one and says so in the reply (eval 12). What a no-skill baseline already does on sonnet and what it does not is in `adr-workspace/iteration-17/README.md`; read it before cutting anything from this skill.
- **design-doc** — writes, reviews *and* updates design docs via interactive discovery; trade-offs are mandatory (zero-cons = red flag). A change with no choice left open gets no doc: the skill says so and asks once, writing a terse mini-doc only when the team's process requires one. A doc whose design changed is edited in place until the system ships; after that its body is left alone and the change goes into a linked amendment (`Amended by` in the original's header is the only edit). Invention by *consequence* is named in the contract: a fact cannot be asserted in one section and asked in Open questions. The "do nothing" alternative is still always written, but only from the pain the user described; with none described it becomes a question. A user-supplied or house template **governs** (its sections become required); only without a template are sections suggestions. A review still asks the author for a template reference (templates live outside the repo), but the template is context, not a checklist: the review **never audits section presence** — it analyzes only the sections the author wrote, and proposes a section only when the existing content calls for one, as a suggestion tied to that content, in the house template's terms when known and the default catalog's otherwise. Diagram convention: the C4 architecture is authored as **Structurizr DSL** (delegating to the `structurizr` skill when present), embedded as a **PNG/SVG image reference with the DSL folded in a `<details>` block** — render via structurizr's `-playwright` image export when reachable, otherwise leave a placeholder with a one-line "render in the manual pass" note; sequence flows stay Mermaid. No "not machine-validated" disclaimer — manual review is assumed; only a *validation* disclaimer is banned. Generated prose is plain active-voice and gets a spelling pass in self-review. Since 1.6.0 the write step also applies the `unslop` skill when it is installed, to the prose written in that turn only; the two prose bullets of step 3 stay as the floor for an install without it (iteration-26 measured their effect), and a review never runs the author's text through it. 1.7.0 made the write step apply the `technical-writing` skill first, when installed, to the same prose and under the same limits, on the argument that it looks each actor up in the repository, which `unslop` cannot do because it removes and never supplies. 1.8.0 takes that call out and is 1.6.0's `SKILL.md` byte for byte, because the one measurement of it found nothing it adds: `design-doc-workspace/iteration-27/` (2026-11-22, claude-sonnet-5-5, two runs per cell, the three skills installed in a project outside the repository and the prompt given alone) compared 1.7.0 with 1.6.0 on evals 1, 4, 6, 7 and 9, and its checks do not separate them: 98/104 against 98/104 on evals 1, 4 and 6, with 0 to 4 agentless passives per document in both versions. The check written for what the change claims, no actor named that nobody established, is met in 6 of 10 documents with 1.6.0 and in 4 of 10 with 1.7.0, and in one 1.7.0 document the pass itself supplied the actor ("não foram discutidos" became "O time ainda não discutiu"). 1.7.0 invoked `technical-writing` in 9 of 10 runs that wrote a document, read its file without invoking it in the tenth, and cost about 29% more tokens and 15% more US$ per document. Two runs measure no rate, and the judge could tell the version from every 1.7.0 reply. The author decided on that evidence to go back, so 1.8.0 was not run again: its text is the `v160` cell of that iteration. Do not put the call back without a check that separates the versions. The same iteration found that the prompt alone does not reach the write step on evals 7 and 9: on eval 7 both versions ask first and write no file, and on eval 9 `design-doc` was invoked in none of eight sessions (see the note on `technical-writing`).
- **structurizr** — authors/edits `workspace.dsl` (C4 model, Structurizr DSL v6+); validation is Docker-only (`structurizr/structurizr validate`), and a missing Docker means "delivered, not validated, here is the command" — never an install attempt. ADR authoring is routed to the team's decision log, not written by this skill. References split into always-read core (`dsl-reference`) plus conditional pattern files for token economy. The export commands are one of those files (`export`), so the hand-off carries only the preview. Theme tag names cited in the references are checked against the theme files the image bundles: a tag the theme does not define draws no icon and no command reports it, and the 1.6.4 example carried two (`Cloud`, `Elastic Load Balancing`) that `amazon-web-services-2025.07` had renamed.
- **mermaid-sequence** — Mermaid sequence diagrams as fenced ` ```mermaid ` blocks; never invent the flow or failure paths; technical detail (endpoint/headers/payload/status) goes in Notes. Validation is local-only and ordered: mermaid-cli Docker image → local `mmdc` → "delivered, not validated, here is the Docker command". mermaid.live may be offered for preview but it renders remotely, so for diagrams carrying internal detail that is the user's call. `references/syntax.md` is always-read (version-portability + escaping gotchas).
- **unslop** — edits prose to remove machine-writing patterns; the one skill that owns that catalog, so that other skills apply it by name instead of each carrying a copy. Rule ids are stable (`S1`–`S21` in `SKILL.md`, `EN*`/`PT*` in one vocabulary file per language under `references/`); a removed rule leaves a gap, because other skills may cite an id. Its form of the shared contract is "remove, never supply": a rule that needs a fact the text lacks deletes the claim or asks. It never edits code, diagram source, quotations, tool-parsed text, or a file that records history. **Explicit only, by its description and not by `disable-model-invocation: true`**: with that flag the Claude Code Skill tool refuses a call that comes from another skill (probed on 2026-11-21, `unslop-workspace/smoke-2026-11-21/README.md`), and the flag is not part of the Agent Skills standard, so a host that ignores it would fall back on the description anyway. The cost is that the description sits in every session's context and that "explicit" is a rate to measure, not a guarantee. - **code-comments** — governs the comments of code an agent writes or changes, in any language; the trigger is "whenever you write or modify code", not a request about comments, so the `SKILL.md` body is kept short (it is read on every coding task) and the before/after pairs sit in `references/examples.md`, read only when a comment resists being made precise. The guidance on what to comment and how to word it condenses chapters 5 and 6 of *The Art of Readable Code* (Boswell & Foucher) in the skill's own words: no text and no example from the book is reproduced, and it must stay that way. Five rules are not the book's and are listed as such in `NOTICE.md`: a reason is written only when the user, the repository or the writer's own decision established it (an unknown reason is reported in the reply, never guessed in the file); comments describe the code and never narrate the edit or the conversation; the scope is the code being changed, plus any comment the change makes false; comments follow the language of the comments already in the file, then the codebase, and only then the conversation; and an existing identifier with a poor name is **not renamed**: the rename is suggested in the reply (the book says to fix the name; the skill does that only for identifiers it introduces). Its form of the shared contract is the first of those rules, and it is the one skill that does not stop to ask, because its deliverable is someone else's code change. No external tooling. - **explain** — explains a topic to one reader and writes or revises texts for other people (messages, emails, replies); one skill for both because the same four questions govern them (who reads and what they know, what contrast is in play, which one or two reasons matter, what the reader does afterwards). The body is a decision procedure plus checks and **has no output template**: the research behind it found no named format (ELI5, Feynman, BLUF, ADEPT) tested against another, while it did find that instructions by adjective ("be simple", "use analogies", "be accurate") are the conditions under which the documented failures of machine-written explanations occur. So the skill instructs procedures: fix the reader from signals, choose the device by the situation, mark the limits, end on something the reader can get wrong. Decisions that are easy to undo by accident: it **explains first** at a stated assumed level and asks first only when two readers would get very different answers (a Socratic gate on a one-off question is banned; the teaching loop is opt-in); an analogy is optional, covers one aspect, and carries its mapping and its breaking point; a closing check is conditional, never a fixed ending; simplifying changes the form and keeps the scope of the claim; no effect size is stated anywhere in the skill, because several came from abstracts or secondary summaries, and no learning gain is claimed. Its form of the shared contract is "facts are recorded, illustrations are built": it is the one skill that has to build content nobody gave it (an example, an analogy, a hypothetical number), so the built parts are shown as illustrations, and it asks only when the reader or the purpose is unknown; in a text for someone else a missing fact becomes a bracketed gap listed after the text. It invokes `unslop`, when installed, only on a text it drafted for a third party: never on an explanation (S13 and S19 would strip the closing check and the analogy) and never on the user's own draft. The before/after pairs sit in `references/techniques.md` and `references/writing.md`; all were written for the skill, and the ones that echoed a source's wording or numbers were replaced. No external tooling. The eval set and the trigger eval set are written (`explain-workspace/evals/evals.json`, `explain-workspace/trigger-evals/trigger_eval.json`). The eval set has 89 frozen checks (`checks-baseline.json`) and a first A/B, `explain-workspace/iteration-1/` (2026-11-21, claude-sonnet-5-5, two runs per cell): 165/178 checks met with the skill read against 151/178 without it. - **technical-writing** — writes, revises and reviews technical documents (README, how-to guide, tutorial, reference, concept page, runbook, release notes, changelog entry, pull request description; a commit message only when the user asks for help with one, since the description leaves it out so that a request to commit does not fire the skill). The body is a procedure (reader, job, facts, draft, actor pass, `unslop`, check) followed by rules in five layers (document, paragraph, sentence, words, procedures and samples); the per-document guidance and the before/after pairs sit in `references/documents.md` and `references/actors.md`. The rule the skill exists for is the first of its contract: **every verb has an actor**, written as the subject of an active verb. It follows a passage of Tanya Reilly's *The Staff Engineer's Path* that the repository's author read in the book and supplied; the same passage quotes Rebecca Johnson's test. The book was not consulted while the skill was written, and no sentence or example of it is in the skill. The rule is about information and not about grammar, and that is what keeps it from contradicting `explain`, whose research found that a nested clause costs the reader more than a passive: a passive that names its actor loses only directness, a passive without one drops a fact. The detector for the grammatical passive is Rebecca Johnson's "by zombies" test, in step 4 and in `references/actors.md`; the skill says next to it that the test finds one of the six hiding places and also fits a state, so that it does not replace the question asked of every verb. Two passives stay (the actor is unknown and the text says so; the verb describes a state). A third, the passive that names its actor with "by" in a paragraph about the object, was in the draft because Gopen and Swan make the case for it, and the author removed it before release: it was the one exception with no checkable criterion, it contradicted the rule as stated, and an active verb keeps the object at the front just as well ("the request then goes to the gateway, which signs it"; `references/actors.md` has the pairs). Do not put it back as a readability fix. Its form of the shared contract is "look the actor up, never pick one": it is a document-writing skill, so it asks, but only after reading the repository, and the same rule covers every command, flag, path, default and output (copied from the repository or from a run that changes nothing; what was not run is listed in the reply). In a revision a passive whose actor the repository does not give **stays as written** and becomes a question, where `unslop` would delete the claim: the two skills differ here on purpose, because this one can read the source and that one edits a text alone. It owns no typography rule and no list of machine-writing patterns; it invokes `unslop`, when installed, after the actor pass. Other skills may call it as they call `unslop`, and then it applies only the actor pass and the rules for the sentence and the words, before `unslop`, and reports nothing. None calls it today: `design-doc` did in 1.7.0 and stopped in 1.8.0 (see its note). `adr` does not call it: a record is short, its Decision is already "We will …", and `unslop` S17 covers the rest for less context. `explain` does not call it either: its texts are messages, and its explanations are kept away even from `unslop`. The description is automatic and borders `explain` ("make this clearer") and `design-doc`; the sweep below checks that it does not fire on their requests, and not which skill wins when both are installed, because the harness loads only the candidate. One case of both installed is on record, from `design-doc-workspace/iteration-27/`: given eval 9 of `design-doc` ("Atualiza a documentação" for a design doc of a system in production), eight sessions with `design-doc`, `technical-writing` and `unslop` installed invoked `design-doc` in none and `technical-writing` in four, and one of those four rewrote the body of the shipped document, which `design-doc` leaves alone. No session ran with `design-doc` installed alone, so this does not show that this skill took the request, and eight runs measure no rate. Decisions that are easy to undo by accident: a new document follows the language of the repository's docs directory when one exists with documents in it, and the language of the conversation otherwise (the author's decision of 2026-11-22; a lone README in another language does not set the language, and a request that names a language wins either way); no limit counted in words (the pstack original has them; Gopen and Swan argue length is not the defect, and `explain` already refuses numbers it cannot support); no pair or example copied from a source (all were written for the skill, and `NOTICE.md` says so); Portuguese is covered in `references/actors.md` because the forms with "se" hide the actor in a way an English-only rule misses. No external tooling. The eval set and the trigger eval set are written (`technical-writing-workspace/evals/evals.json`, `technical-writing-workspace/trigger-evals/trigger_eval.json`); the eval set has 121 frozen checks (`technical-writing-workspace/evals/checks-baseline.json`) and a first A/B, `technical-writing-workspace/iteration-1/` (2026-11-22, claude-sonnet-5-5, two runs per cell): 231/242 checks met with the skill read against 203/242 without it.
