# Maintaining the skills

Read this before changing anything under a `skills/` directory. It is not loaded automatically:
`AGENTS.md` points here so that a description of what the skills are expected to do stays out of
the context of eval runs (see `eval-tools/README.md`).

## Shared contract

- **Record, don't invent** is the shared contract across every skill: document only what the user/repository established; when the request is too vague to fill the sections honestly, ask 2–4 targeted questions instead of fabricating. The questions are the deliverable on a vague ask. `code-comments` is the one skill that does not stop to ask: its deliverable is someone else's code change, so a reason nobody established is left out of the file and reported in the reply.
- **Validation tooling**: today no skill uses an MCP at all, and `adr`, `design-doc`, `unslop` and `code-comments` use no external tooling: `structurizr` validates, previews, and exports through the `structurizr/structurizr` Docker image (PNG/SVG only through its `<version>-playwright` variant; the regular image refuses them), and `mermaid-sequence` validates through the `minlag/mermaid-cli` Docker image with a local `mmdc` as fallback. Without Docker (or the CLI), both ship the artifact with an explicit "not validated" notice plus the command to run later — **never an install attempt, never a remote validator**.

## Per-skill notes

- **adr** — adr-tools-compatible decision log (`NNNN-slug.md`, `doc/adr` default, `.adr-dir` override, `adr init`-style seed on fresh logs, supersede/amend by editing the *old* ADR's Status section only — ADRs are otherwise immutable). The slug is ASCII-only, as adr-tools' own pipeline computes it on Linux (`tr -Ccs [:alnum:] -`): an accented letter becomes a hyphen (`decisões` → `decis-es`), never transliterated and never kept. Modern spelling `Superseded`/`Supersedes` on write; legacy `Superceded` recognized on read. Tool-parsed scaffolding (adr-tools' `Date:` label, the `## Status/Context/Decision/Consequences` headings, status words, supersede/amend verbs) stays canonical English even in a non-English log, because Structurizr's `!adrs` importer and `adr generate` parse those literals; only the prose is translated. A scope check up front hands an open design to `design-doc`, refuses to record a choice not yet made, and leaves `!adrs` wiring to `structurizr`. Since 1.5.0 step 4 applies the `unslop` skill when it is installed, to the title text and section bodies of the record being written; scaffolding, the seed, and every existing record are out of its reach.
- **design-doc** — writes, reviews *and* updates design docs via interactive discovery; trade-offs are mandatory (zero-cons = red flag). A change with no choice left open gets no doc: the skill says so and asks once, writing a terse mini-doc only when the team's process requires one. A doc whose design changed is edited in place until the system ships; after that its body is left alone and the change goes into a linked amendment (`Amended by` in the original's header is the only edit). Invention by *consequence* is named in the contract: a fact cannot be asserted in one section and asked in Open questions. The "do nothing" alternative is still always written, but only from the pain the user described; with none described it becomes a question. A user-supplied or house template **governs** (its sections become required); only without a template are sections suggestions. A review still asks the author for a template reference (templates live outside the repo), but the template is context, not a checklist: the review **never audits section presence** — it analyzes only the sections the author wrote, and proposes a section only when the existing content calls for one, as a suggestion tied to that content, in the house template's terms when known and the default catalog's otherwise. Diagram convention: the C4 architecture is authored as **Structurizr DSL** (delegating to the `structurizr` skill when present), embedded as a **PNG/SVG image reference with the DSL folded in a `<details>` block** — render via structurizr's `-playwright` image export when reachable, otherwise leave a placeholder with a one-line "render in the manual pass" note; sequence flows stay Mermaid. No "not machine-validated" disclaimer — manual review is assumed; only a *validation* disclaimer is banned. Generated prose is plain active-voice and gets a spelling pass in self-review. Since 1.6.0 the write step also applies the `unslop` skill when it is installed, to the prose written in that turn only; the two prose bullets of step 3 stay as the floor for an install without it (iteration-26 measured their effect), and a review never runs the author's text through it.
- **structurizr** — authors/edits `workspace.dsl` (C4 model, Structurizr DSL v6+); validation is Docker-only (`structurizr/structurizr validate`), and a missing Docker means "delivered, not validated, here is the command" — never an install attempt. ADR authoring is routed to the team's decision log, not written by this skill. References split into always-read core (`dsl-reference`) plus conditional pattern files for token economy.
- **mermaid-sequence** — Mermaid sequence diagrams as fenced ` ```mermaid ` blocks; never invent the flow or failure paths; technical detail (endpoint/headers/payload/status) goes in Notes. Validation is local-only and ordered: mermaid-cli Docker image → local `mmdc` → "delivered, not validated, here is the Docker command". mermaid.live may be offered for preview but it renders remotely, so for diagrams carrying internal detail that is the user's call. `references/syntax.md` is always-read (version-portability + escaping gotchas).
- **unslop** — edits prose to remove machine-writing patterns; the one skill that owns that catalog, so that other skills apply it by name instead of each carrying a copy. Rule ids are stable (`S1`–`S21` in `SKILL.md`, `EN*`/`PT*` in one vocabulary file per language under `references/`); a removed rule leaves a gap, because other skills may cite an id. The shared contract becomes "remove, never supply": a rule that needs a fact the text lacks deletes the claim or asks. It never edits code, diagram source, quotations, tool-parsed text, or a file that records history. **Explicit only, by its description and not by `disable-model-invocation: true`**: with that flag the Claude Code Skill tool refuses a call that comes from another skill (probed on 2026-11-21, `unslop-workspace/smoke-2026-11-21/README.md`), and the flag is not part of the Agent Skills standard, so a host that ignores it would fall back on the description anyway. The cost is that the description sits in every session's context and that "explicit" is a rate to measure, not a guarantee. A skill that delegates to it keeps its own short floor of prose rules for an install without `unslop`.
- **code-comments** — governs the comments of code an agent writes or changes, in any language; the trigger is "whenever you write or modify code", not a request about comments, so the `SKILL.md` body is kept short (it is read on every coding task) and the before/after pairs sit in `references/examples.md`, read only when a comment resists being made precise. The guidance on what to comment and how to word it condenses chapters 5 and 6 of *The Art of Readable Code* (Boswell & Foucher) in the skill's own words: no text and no example from the book is reproduced, and it must stay that way. Five rules are not the book's and are listed as such in `NOTICE.md`: a reason is written only when the user, the repository or the writer's own decision established it (an unknown reason is reported in the reply, never guessed in the file); comments describe the code and never narrate the edit or the conversation; the scope is the code being changed, plus any comment the change makes false; comments follow the language of the comments already in the file, then the codebase, and only then the conversation; and an existing identifier with a poor name is **not renamed**: the rename is suggested in the reply (the book says to fix the name; the skill does that only for identifiers it introduces). No external tooling. The eval set is written (`code-comments-workspace/evals/evals.json`) but no eval, behavioral or trigger, has been run, and there is no trigger eval set yet.
