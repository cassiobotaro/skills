# Maintaining the skills

Read this before changing anything under a `skills/` directory. It is not loaded automatically:
`AGENTS.md` points here so that a description of what the skills are expected to do stays out of
the context of eval runs (see `eval-tools/README.md`).

## Shared contract

- **Record, don't invent** is the shared contract across every skill: a skill states as fact only what the user or the repository established, and a gap is never filled with a guess. What a skill does with the gap depends on what it delivers. The skills that write a document or a diagram (`adr`, `design-doc`, `structurizr`, `mermaid-sequence`) ask: when the request is too vague to fill the sections honestly, they ask 2–4 targeted questions instead of fabricating, and the questions are the deliverable. Every other skill states its own form of the contract in its note below, and a new skill does the same instead of being added here as an exception.
- **Validation tooling**: today no skill uses an MCP at all, and `adr`, `design-doc`, `unslop`, `code-comments`, `explain` and `technical-writing` use no external tooling: `structurizr` validates, previews, and exports through the `structurizr/structurizr` Docker image (PNG/SVG only through its `<version>-playwright` variant; the regular image refuses them), and `mermaid-sequence` validates through the `minlag/mermaid-cli` Docker image with a local `mmdc` as fallback. Without Docker (or the CLI), both ship the artifact with an explicit "not validated" notice plus the command to run later — **never an install attempt, never a remote validator**.

## Per-skill notes

- **adr** — adr-tools-compatible decision log (`NNNN-slug.md`, `doc/adr` default, `.adr-dir` override, `adr init`-style seed on fresh logs, supersede/amend by editing the *old* ADR's Status section only — ADRs are otherwise immutable). The slug is ASCII-only, as adr-tools' own pipeline computes it on Linux (`tr -Ccs [:alnum:] -`): an accented letter becomes a hyphen (`decisões` → `decis-es`), never transliterated and never kept. Modern spelling `Superseded`/`Supersedes` on write; legacy `Superceded` recognized on read. Tool-parsed scaffolding (adr-tools' `Date:` label, the `## Status/Context/Decision/Consequences` headings, status words, supersede/amend verbs) stays canonical English even in a non-English log, because Structurizr's `!adrs` importer and `adr generate` parse those literals; only the prose is translated. A scope check up front hands an open design to `design-doc`, refuses to record a choice not yet made, and leaves `!adrs` wiring to `structurizr`. Since 1.5.0 the writing step (step 3; step 4 before 1.6.0) applies the `unslop` skill when it is installed, to the title text and section bodies of the record being written; scaffolding, the seed, and every existing record are out of its reach. Since 1.6.0 the third ingredient of a record is the *trade-off* (what the decision gives up in exchange for what it gets: an alternative passed over, a cost, a constraint), not a negative consequence: when the user gives none the skill asks once what was given up, never supplies one, and when the answer is that there was none it writes the record without one and says so in the reply (eval 12). What a no-skill baseline already does on sonnet and what it does not is in `adr-workspace/iteration-17/README.md`; read it before cutting anything from this skill. Whether the skill is reached when the log is in the project, which the trigger harness cannot show, was probed on 2026-11-22 (`adr-workspace/trigger-evals/in-project-2026-11-22/`, claude-sonnet-5-5, `adr` and `unslop` loaded as plugins from outside the project, the prompt alone): 16 of 16 sessions invoked it, always as the first tool call, on a supersede, on a log with `.adr-dir`, and on two requests that never say "ADR".
- **design-doc** — writes, reviews *and* updates design docs via interactive discovery; trade-offs are mandatory (zero-cons = red flag). A change with no choice left open gets no doc: the skill says so and asks once, writing a terse mini-doc only when the team's process requires one. A doc whose design changed is edited in place until the system ships; after that its body is left alone and the change goes into a linked amendment (`Amended by` in the original's header is the only edit). Invention by *consequence* is named in the contract: a fact cannot be asserted in one section and asked in Open questions. The "do nothing" alternative is still always written, but only from the pain the user described; with none described it becomes a question. A user-supplied or house template **governs** (its sections become required); only without a template are sections suggestions. A review still asks the author for a template reference (templates live outside the repo), but the template is context, not a checklist: the review **never audits section presence** — it analyzes only the sections the author wrote, and proposes a section only when the existing content calls for one, as a suggestion tied to that content, in the house template's terms when known and the default catalog's otherwise. Diagram convention: the C4 architecture is authored as **Structurizr DSL** (delegating to the `structurizr` skill when present), embedded as a **PNG/SVG image reference with the DSL folded in a `<details>` block** — render via structurizr's `-playwright` image export when reachable, otherwise leave a placeholder with a one-line "render in the manual pass" note; sequence flows stay Mermaid. No "not machine-validated" disclaimer — manual review is assumed; only a *validation* disclaimer is banned. Generated prose is plain active-voice and gets a spelling pass in self-review. - **code-comments** — governs the comments of code an agent writes or changes, in any language; the trigger is "whenever you write or modify code", not a request about comments, so the `SKILL.md` body is kept short (it is read on every coding task) and the before/after pairs sit in `references/examples.md`, read only when a comment resists being made precise. The guidance on what to comment and how to word it condenses chapters 5 and 6 of *The Art of Readable Code* (Boswell & Foucher) in the skill's own words: no text and no example from the book is reproduced, and it must stay that way. Five rules are not the book's and are listed as such in `NOTICE.md`: a reason is written only when the user, the repository or the writer's own decision established it (an unknown reason is reported in the reply, never guessed in the file); comments describe the code and never narrate the edit or the conversation; the scope is the code being changed, plus any comment the change makes false; comments follow the language of the comments already in the file, then the codebase, and only then the conversation; and an existing identifier with a poor name is **not renamed**: the rename is suggested in the reply (the book says to fix the name; the skill does that only for identifiers it introduces). - **explain** — explains a topic to one reader and writes or revises texts for other people (messages, emails, replies); one skill for both because the same four questions govern them (who reads and what they know, what contrast is in play, which one or two reasons matter, what the reader does afterwards). The body is a decision procedure plus checks and **has no output template**: the research behind it found no named format (ELI5, Feynman, BLUF, ADEPT) tested against another, while it did find that instructions by adjective ("be simple", "use analogies", "be accurate") are the conditions under which the documented failures of machine-written explanations occur. So the skill instructs procedures: fix the reader from signals, choose the device by the situation, mark the limits, end on something the reader can get wrong. Decisions that are easy to undo by accident: it **explains first** at a stated assumed level and asks first only when two readers would get very different answers (a Socratic gate on a one-off question is banned; the teaching loop is opt-in); an analogy is optional, covers one aspect, and carries its mapping and its breaking point; a closing check is conditional, never a fixed ending; simplifying changes the form and keeps the scope of the claim; no effect size is stated anywhere in the skill, because several came from abstracts or secondary summaries, and no learning gain is claimed. Its form of the shared contract is "facts are recorded, illustrations are built": it is the one skill that has to build content nobody gave it (an example, an analogy, a hypothetical number), so the built parts are shown as illustrations, and it asks only when the reader or the purpose is unknown; in a text for someone else a missing fact becomes a bracketed gap listed after the text. It invokes `unslop`, when installed, only on a text it drafted for a third party: never on an explanation (S13 and S19 would strip the closing check and the analogy) and never on the user's own draft. - **technical-writing** — writes, revises and reviews technical documents (README, how-to guide, tutorial, reference, concept page, runbook, release notes, changelog entry, pull request description; a commit message only when the user asks for help with one, since the description leaves it out so that a request to commit does not fire the skill). The rule the skill exists for is the first of its contract: **every verb has an actor**, written as the subject of an active verb. It follows a passage of Tanya Reilly's *The Staff Engineer's Path* that the repository's author read in the book and supplied; the same passage quotes Rebecca Johnson's test. The book was not consulted while the skill was written, and no sentence or example of it is in the skill. The rule is about information and not about grammar, and that is what keeps it from contradicting `explain`, whose research found that a nested clause costs the reader more than a passive: a passive that names its actor loses only directness, a passive without one drops a fact. The detector for the grammatical passive is Rebecca Johnson's "by zombies" test, in step 4 and in `references/actors.md`; the skill says next to it that the test finds one of the six hiding places and also fits a state, so that it does not replace the question asked of every verb. Two passives stay (the actor is unknown and the text says so; the verb describes a state). A third, the passive that names its actor with "by" in a paragraph about the object, was in the draft because Gopen and Swan make the case for it, and the author removed it before release: it was the one exception with no checkable criterion, it contradicted the rule as stated, and an active verb keeps the object at the front just as well ("the request then goes to the gateway, which signs it"; `references/actors.md` has the pairs). Do not put it back as a readability fix. Its form of the shared contract is "look the actor up, never pick one": it is a document-writing skill, so it asks, but only after reading the repository, and the same rule covers every command, flag, path, default and output (copied from the repository or from a run that changes nothing; what was not run is listed in the reply).
