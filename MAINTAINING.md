# Maintaining the skills

Read this before changing anything under a `skills/` directory. It is not loaded automatically:
`AGENTS.md` points here so that a description of what the skills are expected to do stays out of
the context of eval runs (see `eval-tools/README.md`).

## Shared contract

- **Record, don't invent** is the shared contract across every skill: a skill states as fact only what the user or the repository established, and a gap is never filled with a guess. What a skill does with the gap depends on what it delivers. The skills that write a document or a diagram (`adr`, `design-doc`, `structurizr`, `mermaid-sequence`) ask: when the request is too vague to fill the sections honestly, they ask 2–4 targeted questions instead of fabricating, and the questions are the deliverable. Every other skill states its own form of the contract in its note below, and a new skill does the same instead of being added here as an exception.
- **Validation tooling**: today no skill uses an MCP at all, and `adr`, `design-doc`, `unslop`, `code-comments` and `explain` use no external tooling: `structurizr` validates, previews, and exports through the `structurizr/structurizr` Docker image (PNG/SVG only through its `<version>-playwright` variant; the regular image refuses them), and `mermaid-sequence` validates through the `minlag/mermaid-cli` Docker image with a local `mmdc` as fallback. Without Docker (or the CLI), both ship the artifact with an explicit "not validated" notice plus the command to run later — **never an install attempt, never a remote validator**.

## Per-skill notes

- **adr** — adr-tools-compatible decision log (`NNNN-slug.md`, `doc/adr` default, `.adr-dir` override, `adr init`-style seed on fresh logs, supersede/amend by editing the *old* ADR's Status section only — ADRs are otherwise immutable). The slug is ASCII-only, as adr-tools' own pipeline computes it on Linux (`tr -Ccs [:alnum:] -`): an accented letter becomes a hyphen (`decisões` → `decis-es`), never transliterated and never kept. Modern spelling `Superseded`/`Supersedes` on write; legacy `Superceded` recognized on read. Tool-parsed scaffolding (adr-tools' `Date:` label, the `## Status/Context/Decision/Consequences` headings, status words, supersede/amend verbs) stays canonical English even in a non-English log, because Structurizr's `!adrs` importer and `adr generate` parse those literals; only the prose is translated. A scope check up front hands an open design to `design-doc`, refuses to record a choice not yet made, and leaves `!adrs` wiring to `structurizr`. Since 1.5.0 step 4 applies the `unslop` skill when it is installed, to the title text and section bodies of the record being written; scaffolding, the seed, and every existing record are out of its reach.
- **design-doc** — writes, reviews *and* updates design docs via interactive discovery; trade-offs are mandatory (zero-cons = red flag). A change with no choice left open gets no doc: the skill says so and asks once, writing a terse mini-doc only when the team's process requires one. A doc whose design changed is edited in place until the system ships; after that its body is left alone and the change goes into a linked amendment (`Amended by` in the original's header is the only edit). Invention by *consequence* is named in the contract: a fact cannot be asserted in one section and asked in Open questions. The "do nothing" alternative is still always written, but only from the pain the user described; with none described it becomes a question. A user-supplied or house template **governs** (its sections become required); only without a template are sections suggestions. A review still asks the author for a template reference (templates live outside the repo), but the template is context, not a checklist: the review **never audits section presence** — it analyzes only the sections the author wrote, and proposes a section only when the existing content calls for one, as a suggestion tied to that content, in the house template's terms when known and the default catalog's otherwise. Diagram convention: the C4 architecture is authored as **Structurizr DSL** (delegating to the `structurizr` skill when present), embedded as a **PNG/SVG image reference with the DSL folded in a `<details>` block** — render via structurizr's `-playwright` image export when reachable, otherwise leave a placeholder with a one-line "render in the manual pass" note; sequence flows stay Mermaid. No "not machine-validated" disclaimer — manual review is assumed; only a *validation* disclaimer is banned. Generated prose is plain active-voice and gets a spelling pass in self-review. Since 1.6.0 the write step also applies the `unslop` skill when it is installed, to the prose written in that turn only; the two prose bullets of step 3 stay as the floor for an install without it (iteration-26 measured their effect), and a review never runs the author's text through it.
- **structurizr** — authors/edits `workspace.dsl` (C4 model, Structurizr DSL v6+); validation is Docker-only (`structurizr/structurizr validate`), and a missing Docker means "delivered, not validated, here is the command" — never an install attempt. ADR authoring is routed to the team's decision log, not written by this skill. References split into always-read core (`dsl-reference`) plus conditional pattern files for token economy.
- **mermaid-sequence** — Mermaid sequence diagrams as fenced ` ```mermaid ` blocks; never invent the flow or failure paths; technical detail (endpoint/headers/payload/status) goes in Notes. Validation is local-only and ordered: mermaid-cli Docker image → local `mmdc` → "delivered, not validated, here is the Docker command". mermaid.live may be offered for preview but it renders remotely, so for diagrams carrying internal detail that is the user's call. `references/syntax.md` is always-read (version-portability + escaping gotchas).
- **unslop** — edits prose to remove machine-writing patterns; the one skill that owns that catalog, so that other skills apply it by name instead of each carrying a copy. Rule ids are stable (`S1`–`S21` in `SKILL.md`, `EN*`/`PT*` in one vocabulary file per language under `references/`); a removed rule leaves a gap, because other skills may cite an id. Its form of the shared contract is "remove, never supply": a rule that needs a fact the text lacks deletes the claim or asks. It never edits code, diagram source, quotations, tool-parsed text, or a file that records history. **Explicit only, by its description and not by `disable-model-invocation: true`**: with that flag the Claude Code Skill tool refuses a call that comes from another skill (probed on 2026-11-21, `unslop-workspace/smoke-2026-11-21/README.md`), and the flag is not part of the Agent Skills standard, so a host that ignores it would fall back on the description anyway. The cost is that the description sits in every session's context and that "explicit" is a rate to measure, not a guarantee. The first measurement is the routine check of 2026-11-21 on claude-sonnet-5-5 (`unslop-workspace/trigger-evals/serial-2026-11-21-routine-sonnet.json`, one sweep, 3 runs per query): 0/30 false fires with the canary at 3/3, including the two boundary queries that ask for this job without naming the skill, and 21/30 on the positives. The nine misses are three queries that point at an earlier message ("the summary you just wrote", "o e-mail que eu colei acima", "unslop that"). Six captured transcripts (`transcripts-noprior-sonnet/` there) show each session answering in prose that the conversation holds no earlier text, so a single-message session cannot fire them and they say nothing about the description; the other seven positives scored 21/21. The set now carries the text in those three queries, which scored 10/10 each at ten runs with the canary at 10/10 (`serial-2026-11-21-pastedtext-probe-sonnet-n10.json`); it no longer has a query that refers to an earlier message, which this harness cannot measure, and no full sweep has been run on the new set. The eval set has 55 frozen checks (`unslop-workspace/evals/checks-baseline.json`) and a first A/B, `unslop-workspace/iteration-1/` (2026-11-21, claude-sonnet-5-5, two runs per cell): 109/110 checks met with the skill read against 98/110 without it, or 95/102 once a run that a shell alias derailed is left out. Both cells remove the tells and leave code, quotations and the accepted ADR alone; what the skill adds is on the side of "without changing its meaning and without adding a fact" (a claim made stronger in both runs without the skill, a bare assertion kept and a sentence invented in one run each). Every prompt names the skill, so the cell without it measures what the model makes of the word, and two runs measure no rate. A skill that delegates to it keeps its own short floor of prose rules for an install without `unslop`.
- **code-comments** — governs the comments of code an agent writes or changes, in any language; the trigger is "whenever you write or modify code", not a request about comments, so the `SKILL.md` body is kept short (it is read on every coding task) and the before/after pairs sit in `references/examples.md`, read only when a comment resists being made precise. The guidance on what to comment and how to word it condenses chapters 5 and 6 of *The Art of Readable Code* (Boswell & Foucher) in the skill's own words: no text and no example from the book is reproduced, and it must stay that way. Five rules are not the book's and are listed as such in `NOTICE.md`: a reason is written only when the user, the repository or the writer's own decision established it (an unknown reason is reported in the reply, never guessed in the file); comments describe the code and never narrate the edit or the conversation; the scope is the code being changed, plus any comment the change makes false; comments follow the language of the comments already in the file, then the codebase, and only then the conversation; and an existing identifier with a poor name is **not renamed**: the rename is suggested in the reply (the book says to fix the name; the skill does that only for identifiers it introduces). Its form of the shared contract is the first of those rules, and it is the one skill that does not stop to ask, because its deliverable is someone else's code change. No external tooling. The eval set (`code-comments-workspace/evals/evals.json`) has 43 frozen checks (`checks-baseline.json`, which adds the judged kind `negative`). Its first A/B is `code-comments-workspace/iteration-1/` (2026-11-21, claude-sonnet-5-5, two runs per cell): 84/86 checks met with the skill read against 79/86 without it. The one separation is eval 5, where only the skill makes the reply suggest renaming `d` without doing it (2/2 against 0/2); without the skill the model already wrote no restating or narrating comment, kept the file's language and invented no reason for a constant, and both cells gave a reason for the injectable clock in eval 6. Two runs measure no rate, and the brief told the executor to read the skill, so that A/B says nothing about triggering. The trigger set (`code-comments-workspace/trigger-evals/trigger_eval.json`) pastes the code in each query, because this repository has no code for a session to open, and six of its ten positives never mention comments. A pilot of four captured sessions (`transcripts-pilot-sonnet/` there) found the skill invoked as the first tool call or not at all, never after the code was written, so the strict count of the harness fits this skill. The routine check of 2026-11-21 on claude-sonnet-5-5 (`serial-2026-11-21-routine-sonnet.json`, one sweep, 3 runs per query) gave 0/30 false fires with the canary at 3/3, 12/12 on the four positives that name comments or docstrings, and 9/18 on the six that do not (script 3/3, bug fix 3/3, refactor 2/3, test 1/3, new function 0/3, one-line change 0/3). Three runs do not rank those six queries, as thirty captured sessions of the same day show (`transcripts-implicit-probe-sonnet-n10/`, ten per query): the test query that scored 1/3 scored 10/10; the one-line change stayed at 0/10, every session answering in prose with the changed code; the new function scored 3/10 as the first tool call, with five answers in prose, one session that invoked the skill after searching the repository and one that searched and never invoked it. That last query says "next to this one" and pastes `slugify`, a function that also exists in the eval fixtures, so two sessions went looking for the file. Reworded with nothing to look for (`dedupe_filename`, a name absent from the repository), it scored 10/10 (`transcripts-newfunction-reworded-sonnet-n10/`), and that version is the one in the set. What holds is one query: the one-line change, 0/13 over the sweep and the probe, where the session returns the changed code without consulting the skill. No full sweep has been run on the set as it now stands.
- **explain** — explains a topic to one reader and writes or revises texts for other people (messages, emails, replies); one skill for both because the same four questions govern them (who reads and what they know, what contrast is in play, which one or two reasons matter, what the reader does afterwards). The body is a decision procedure plus checks and **has no output template**: the research behind it found no named format (ELI5, Feynman, BLUF, ADEPT) tested against another, while it did find that instructions by adjective ("be simple", "use analogies", "be accurate") are the conditions under which the documented failures of machine-written explanations occur. So the skill instructs procedures: fix the reader from signals, choose the device by the situation, mark the limits, end on something the reader can get wrong. Decisions that are easy to undo by accident: it **explains first** at a stated assumed level and asks first only when two readers would get very different answers (a Socratic gate on a one-off question is banned; the teaching loop is opt-in); an analogy is optional, covers one aspect, and carries its mapping and its breaking point; a closing check is conditional, never a fixed ending; simplifying changes the form and keeps the scope of the claim; no effect size is stated anywhere in the skill, because several came from abstracts or secondary summaries, and no learning gain is claimed. Its form of the shared contract is "facts are recorded, illustrations are built": it is the one skill that has to build content nobody gave it (an example, an analogy, a hypothetical number), so the built parts are shown as illustrations, and it asks only when the reader or the purpose is unknown; in a text for someone else a missing fact becomes a bracketed gap listed after the text. It invokes `unslop`, when installed, only on a text it drafted for a third party: never on an explanation (S13 and S19 would strip the closing check and the analogy) and never on the user's own draft. The before/after pairs sit in `references/techniques.md` and `references/writing.md`; all were written for the skill, and the ones that echoed a source's wording or numbers were replaced. No external tooling. The eval set and the trigger eval set are written (`explain-workspace/evals/evals.json`, `explain-workspace/trigger-evals/trigger_eval.json`). The eval set has 89 frozen checks (`checks-baseline.json`) and a first A/B, `explain-workspace/iteration-1/` (2026-11-21, claude-sonnet-5-5, two runs per cell): 165/178 checks met with the skill read against 151/178 without it. The clearest effect is the teaching loop, one idea and one question with the skill against a lecture and a list of exercises without it; in texts for someone else the skill keeps the claim of the source and drops the stock closer. Five checks fail in both cells (a borrowed term left undefined in evals 1 and 4, the answer not in the first three sentences of eval 3, a simplified text longer than its source, more than three lines on what changed), and an analogy carried no stated limit in three runs of four. Two runs measure no rate. 1.0.1 repeats one rule of the body in the "Before sending" list, the three lines at most on what changed in a revision of the user's draft: the rule sat in one sentence of section 5 and both runs of 1.0.0 gave four or five bullets. The trigger text is automatic and broad ("explain X", "help me reply"), so the first trigger sweep looked at the negatives: the routine check of 2026-11-21 on claude-sonnet-5-5 (`explain-workspace/trigger-evals/serial-2026-11-21-routine-sonnet.json`, one sweep, 3 runs per query) gave 0/33 false fires with the canary at 3/3, and 30/33 on the positives. The three misses are one query, since replaced, the only positive that named a file ("why does internal/sync/worker.go take the lock twice in drain()?"); probed the same day at ten runs it scored 0/10 with the canary at 10/10 (`serial-2026-11-21-workergo-probe-sonnet-n10.json` in the same directory). Three captured transcripts (`transcripts-workergo-sonnet/` there) show why: that file does not exist in this repository, so each session searched for it, found nothing, and replied that the file is not here, with nothing left to explain. The misses came from the query and not from the description, so the set now asks the same question with the code pasted in it: that query scored 10/10 at ten runs with the canary at 10/10 (`serial-2026-11-21-pastedcode-probe-sonnet-n10.json`). The routine sweep above ran on the old query, and no full sweep has been run on the new set.
